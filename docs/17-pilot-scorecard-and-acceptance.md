# 17 — Pilot scorecard & Acceptance (паспорт пилота)

Цель: превратить пилот из “попробовали” в измеримый результат, на основании которого принимается решение о production.

## 1) Договорённости пилота (фиксируются до старта)

- Период пилота: (даты)
- Локации: (список)
- Кол-во экранов: (N)
- Ответственные:
  - со стороны клиента: IT owner, Operator owner
  - со стороны продукта: Owner/PM/PO
- Сценарии, которые обязаны работать:
  - публикация контента/расписания
  - overlay (manual + 1 источник данных)
  - диагностика offline/ошибок

## 2) Критерии успеха (go/no-go)

### Must pass (без этого нельзя в прод)

- Playback uptime ≥ 99.9% (по данным heartbeat/as-run).
- Нет “black screen” без fallback.
- Online rate ≥ 95% в рабочее время (или согласованный порог с учётом сети).
- Есть audit изменений и as-run отчёт по периоду.

### Should pass (важно, но можно улучшать)

- Time-to-publish P95 ≤ 10 минут.
- Overlay latency P95 ≤ 2 секунды (на нормальной сети).
- Overlay adoption ≥ 50% экранов пилота.

## 3) Чек-лист приёмки (пошагово)

### Контент/расписание

- Загрузка видео/картинки проходит и видна в библиотеке.
- Draft не влияет на экраны.
- Publish меняет показ на устройствах.
- Rollback (если включён) возвращает предыдущую версию.

### Устройства

- enroll → устройство появляется в админке
- assignment → начинает показывать канал
- offline → отображается как offline, с последним временем связи

### Overlay

- manual update → видно на экране
- REST pull источник → обновляет данные без ручных действий

### Надёжность

- отключение интернета на 30 минут → воспроизведение не останавливается
- битый asset → не валит плейлист целиком

## 4) Pilot report (итоговый отчёт)

Структура отчёта:
- Сводка (1 страница): достигли/не достигли
- Метрики (таблица):
  - time-to-publish p50/p95
  - uptime
  - online rate
  - overlay latency
  - overlay adoption
- Инциденты (список, причины, MTTR)
- Топ-5 улучшений (по impact/effort)
- Решение: Go to R1 / Extend pilot / Stop
