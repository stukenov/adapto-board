# 16 — Release notes, rollout и коммуникации

Цель: выпускать продукт предсказуемо, без “сломали экраны ночью”.

## 1) Политика совместимости (Player API)

- Player API versioned (`/api/player/v1/...` или заголовок версии).
- Поддерживаем минимум N-1 версию игрока в backend (пока все устройства не обновлены).
- Breaking changes запрещены без:
  - заранее объявленного окна,
  - стратегии миграции,
  - внятного rollback.

## 2) Rollout стратегия (Android TV)

Обновления приложения управляются через MDM/managed Google Play:
- канареечная группа устройств (5–10%)
- затем 25% → 50% → 100%

Продуктовый артефакт на каждый релиз:
- список групп и порядок rollout
- критерии “стоп/откат”

## 3) Release readiness checklist (обязательный)

- SLO/алерты на месте (app/db/online rate/publish errors)
- миграции проверены (и есть plan rollback)
- нет regressions на поддерживаемых Android TV устройствах
- обновлены release notes
- определён “owner on call” на 24–72 часа после релиза

## 4) Шаблон release notes (для клиентов)

- Version / Date
- Что нового (1–5 пунктов)
- Изменения поведения (если есть)
- Исправления (bugs)
- Известные ограничения
- Требования/совместимость (минимальная версия player)
- Контакты поддержки и процедура инцидента

## 5) Коммуникация со стейкхолдерами

Обязательные аудитории:
- оператор контента (что поменялось в UI)
- ИТ/безопасность (что поменялось в доступах/логах/инфре)
- интегратор (изменения API/форматов)

## 6) Инциденты (продуктовая часть)

После P0 инцидента продакт фиксирует:
- impact (сколько экранов/тенантов)
- время обнаружения/восстановления
- первопричину и “почему не поймали”
- корректирующие действия:
  - продуктовые (UX, ограничения, фичи для диагностики)
  - процессные (чек-лист, тесты)
