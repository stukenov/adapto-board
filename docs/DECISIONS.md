# Decisions (ADR-lite)

## D001 — Kotlin-only по всему стеку

- Решение: backend + admin UI + Android TV app делаем на Kotlin.
- Причина: скорость команды, единая модель данных, меньше контекстов.
- Компромисс: web UI делаем “операторским” и простым, без тяжёлого фронтенд-стека.

## D002 — Android TV как единственная платформа v1

- Решение: поддерживаем только Android TV.
- Причина: минимизация QA матрицы и операционной поддержки.
- Компромисс: часть клиентов с Tizen/webOS откладываем на R2+.

## D003 — Один монолит вместо микросервисов

- Решение: один Ktor монолит с внутренними модулями.
- Причина: меньше систем, проще деплой/наблюдаемость, быстрее пилот.
- Компромисс: нужна дисциплина модульных границ и миграционный план на рост.

## D004 — SSE для overlay

- Решение: realtime слой делаем через SSE.
- Причина: проходит через прокси проще, чем WS; реализация проще.
- Компромисс: соединения долгоживущие, нужно следить за ресурсами.

## D005 — Postgres как “центр правды”

- Решение: Postgres — единственная обязательная внешняя система в v1.
- Причина: транзакции, индексы, ретеншн, простота эксплуатации.
- Компромисс: аккуратно проектировать as-run объёмы и ретеншн.

## D006 — Admin UI только web

- Решение: админка — только web UI.
- Причина: проще внедрение в enterprise (доступ по URL), быстрее rollout и поддержка.
- Компромисс: web-ограничения/кроссбраузерность; интерактивность ограничиваем в v1.

## D007 — Admin Web v1: server-rendered UI (SSR) внутри Ktor

- Решение: админка v1 — server-rendered web UI, отдаваемая тем же Ktor-монолитом (Kotlin templates через `kotlinx.html`/Ktor HTML DSL).
- Причина: быстрее MVP и меньше команда (не нужен отдельный frontend build и отдельная разработка UI-стека).
- Компромисс: меньше интерактивности (без drag&drop/визуальных редакторов); UX делаем “операторский”, не “дизайнерский”.

## D008 — Persistence v1: Exposed

- Решение: persistence слой v1 делаем на Exposed.
- Причина: Kotlin-native, быстрее старт и ниже сложность, чем codegen/DSL jOOQ в MVP.
- Компромисс: при росте сложности запросов возможен переход на jOOQ точечно.

## D009 — Overlay patch format v1: domain patch

- Решение: `state + patch`, где `patch` — обновления виджетов по `widgetId` (domain patch).
- Причина: проще применить на Android TV, проще дебажить и логировать.
- Компромисс: нужно явно версионировать схему виджетов и валидировать входные данные.

## D010 — GTM-режим: single-tenant per deployment (до product/market fit)

- Решение: на ранней стадии разворачиваем отдельный инстанс продукта на клиента (1 tenant per environment), при этом модель данных остаётся tenant-aware.
- Причина: снижает риск многотенантных ошибок, ускоряет внедрение и упрощает security/procurement (“у вас отдельный контур”).
- Компромисс: выше инфраструктурные затраты на клиента; окупается скоростью пилотов и меньшей стоимостью разработки/поддержки.

## D011 — Support-функции в составе Admin Web (без отдельной support системы)

- Решение: “support-grade UX” (ops dashboards, device detail, support bundle, alerts) реализуем в той же SSR админке и том же монолите.
- Причина: это снижает стоимость поддержки и ускоряет triage в пилотах; отдельная support система на старте — лишняя инфраструктура.
- Компромисс: нужен аккуратный RBAC (внутренние роли) и audit всех “опасных” действий.

## D012 — Rollout per company: через окружения и release rings (до 10 клиентов)

- Решение: выкатки backend делаем “per environment” (D010) через CI/CD + ручные approvals и кольца `CANARY/STABLE`; per-tenant feature flags — только если переходим к shared multi-tenant.
- Причина: это дешевле, чем строить отдельный оркестратор/админку деплоя, и безопаснее при маленькой команде.
- Компромисс: операционные файлы окружений и дисциплина релизного процесса становятся критичными.

## D013 — Outbound automation: только consent-based, с audit и suppression

- Решение: любые email/SMS/WhatsApp/Telegram/calls очереди строим только вокруг consent/policy checks, suppression list и аудита; контакты без законного основания не отправляются автоматически.
- Причина: провайдеры и законы жёстко наказывают спам; “серый” outbound разрушает доменную репутацию и блокирует каналы.
- Компромисс: больше ручной работы на раннем этапе (human-in-the-loop), но меньше рисков и дешевле в итоге.

## D014 — LLM enrichment: минимизация PII и воспроизводимость

- Решение: LLM используем для парсинга/нормализации/классификации и черновиков, но логируем `prompt_version/model/input_hash` и валидируем JSON-schema; не кормим модель лишними PII.
- Причина: это даёт качество данных и повторяемость при ограниченном бюджете и без “магии”.
- Компромисс: нужно поддерживать схемы/версии промптов и fallback на ручную разметку.
