Ниже — **универсальный PRD** для **Playout Edge (корп-TV / digital signage, multi-tenant)** в философии “делаем меньше, но только самое важное”. Без мусора, без “а давайте ещё блокчейн” — только то, что реально продаётся, внедряется и работает 24/7.

---

# PRD: Playout Edge — Corporate TV & Digital Signage Platform (Multi-Tenant)

## 1) Введение

### 1.1. Проблема

Организациям нужно централизованно управлять контентом на тысячах экранов (офисы, филиалы, стойки обслуживания), при этом:

* контент должен быть **контролируемым** (кто/что/когда показывалось),
* персонализация должна быть **дешёвой** (не отдельное видео на каждый экран),
* эксплуатация — **безопасной** (минимум ручных действий, максимум наблюдаемости).

### 1.2. Решение (суть продукта)

Playout Edge — платформа, которая:

* управляет **каналами** (плейлист/расписание/правила показа),
* управляет **парком устройств** (экраны, плееры, филиалы),
* даёт **realtime слой данных** поверх видео (очереди, KPI, меню, уведомления),
* обеспечивает **аудит**: что реально показывалось (as-run).

Один и тот же видеоконтент кэшируется и переиспользуется; персонализация делается **данными**, а не “уникальными видео-версии на каждый экран”.

---

## 2) Цели и не-цели

### 2.1. Цели (Must Win)

1. Запустить пилот за 2–4 недели на 50–200 экранах без героизма.
2. Масштабироваться до 10k+ экранов без деградации управления и стоимости.
3. Дать бизнесу: “я могу за 5 минут обновить инфу на всех экранах”.
4. Дать ИТ: безопасность, RBAC, аудит, мониторинг, предсказуемый rollout.

### 2.2. Не-цели (явно)

* Не строим “телевизионный broadcast-центр” уровня национального ТВ.
* Не делаем сложный графический редактор/After Effects внутри продукта.
* Не делаем per-user уникальный видеопоток (персонализация — через overlay).
* Не строим рекламную платформу (FAST/SSAI) в базовом релизе.

---

## 3) Определение успеха (метрики)

### 3.1. Продуктовые

* **Time-to-publish**: от “загрузил/обновил” до “видно на экране” ≤ 2 мин (P50), ≤ 10 мин (P95).
* **Uptime playback** (на уровне плейлиста): ≥ 99.9%/мес.
* **Доля экранов online**: ≥ 95% в любой момент (учитывая реальные сети).
* **Adoption overlays**: ≥ 60% экранов используют data-layer (это то, за что платят).

### 3.2. Операционные

* MTTR (критичный сбой) ≤ 30 минут.
* Изменения расписания с аудитом: 100% изменений логируются.
* Стоимость доставки: контролируется лимитами и профилями качества.

---

## 4) Персоны

1. **Оператор контента** (маркетинг/HR/админ): хочет “залил → показалось”.
2. **Операционный админ** (служба эксплуатации): хочет стабильность, статусы, алерты.
3. **ИТ/Безопасность**: SSO/RBAC, ограничения, аудит, минимизация рисков.
4. **Интегратор** (разработчик клиента): подключает очереди, KPI, меню, ERP/CRM.

---

## 5) Основные сценарии (Jobs-to-be-Done)

### 5.1. Базовый “канал”

* Создать канал для филиала/группы.
* Добавить контент (видео/картинки).
* Настроить расписание (дни/часы/паузы).
* Подключить устройства → контент показывается.

### 5.2. Data-layer поверх видео

* Подключить источник данных (очередь/табло/меню).
* Задать шаблон оверлея (минимальный набор виджетов).
* Проверить синхронизацию и обновление в реальном времени.

### 5.3. Управление парком

* Зарегистрировать устройство (авто-привязка к тенанту).
* Назначить группе/каналу.
* Видеть статус: online/offline, версия плеера, ошибки, “последний кадр/heartbeat”.

### 5.4. Аудит

* Понять “что реально показывалось” (as-run) за период.
* Понять “кто изменил” (audit log) и откатить версию расписания.

---

## 6) MVP-скоуп (минимум, который продаётся)

### 6.1. Контент и библиотека (MVP)

**Must:**

* Ingest: upload файла + базовая валидация (формат/длительность).
* Авто-нормализация в один “стандартный” профиль (чтобы плееры жили).
* Теги: название, длительность, папки/проекты.
* Права показа: “активно с/до”, “разрешено в тенанте”.

**Nice позже:**

* Мульти-профили качества, субтитры, много аудио дорожек.

### 6.2. Расписание/каналы (MVP)

**Must:**

* Канал = набор “слотов” по дням/часам.
* Версионирование расписаний: Draft → Publish.
* Автоподкладка (fallback): если контента нет/ошибка → “служебный экран”.

**Nice позже:**

* Сложные правила (priority windows, контентные кампании, A/B).

### 6.3. Fleet management (MVP)

**Must:**

* Регистрация устройства (device code / QR).
* Группы устройств (филиал/этаж/тип).
* Назначение: устройство → канал.
* Heartbeat + базовые метрики (CPU/RAM/network optional).
* Remote config pull (плеер периодически забирает конфиг).

**Nice позже:**

* Remote commands (reboot/app restart), screenshots, deep diagnostics.

### 6.4. Overlay/Data layer (MVP)

**Must:**

* Один транспорт: **SSE** (простое и надёжное через прокси).
* Модель: `state + patch` (полное состояние + диффы).
* Минимальный набор виджетов:

  1. текст/бегущая строка,
  2. таблица очереди (N строк),
  3. KPI плитки,
  4. изображение/QR.
* Подключение источника данных:

  * REST pull (периодический fetch),
  * webhook push (при наличии),
  * ручной ввод (для пилотов).

**Nice позже:**

* WS, сложные макеты, правила видимости по ролям.

### 6.5. Аудит и as-run (MVP)

**Must:**

* Audit log: кто/когда/что поменял (канал, расписание, устройство).
* As-run: канал/устройство → что показывалось по времени (достаточно coarse).

---

## 7) UX/Принципы (чтобы не сделать “админку из 2008”)

1. **Одна главная сущность: Канал.** Всё крутится вокруг него.
2. **Два клика до “опубликовать”.** Никаких лабиринтов.
3. **Безопасный по умолчанию:** роли, read-only, превью, подтверждение публикации.
4. **Пилот-first:** всё должно работать без интегратора (manual data mode).

---

## 8) Требования к платформе

### 8.1. Multi-tenant

* Жёсткая изоляция данных между тенантами.
* Квоты: число устройств, каналы, объём контента, RPS API, лимит трафика.

### 8.2. Надёжность

* Любая ошибка контента/сети не должна “гасить экран”: только fallback.
* Должен быть “режим стабильности”: запрет изменений (read-only ops mode).

### 8.3. Безопасность

* SSO/OIDC (минимум: JWT + роли).
* RBAC: Admin / Operator / Viewer / Integrator.
* Подписанные URL/TTL для доступа к плейлистам/контенту (групповые, не per-user).
* Audit обязателен.

---

## 9) Технический дизайн (на уровне PRD, без излишнего дрочева)

### 9.1. Компоненты

1. **Control Plane API**: users/tenants/channels/schedules/devices/audit
2. **Ingest Workers**: нормализация, хранение, индексация
3. **Overlay Service**: SSE stream + коннекторы источников
4. **Delivery**: origin + CDN
5. **Player Apps/SDK**: воспроизведение + overlays + device agent

### 9.2. Данные (минимальные таблицы)

* tenants
* users, roles
* devices, device_groups
* channels
* schedules (versions), schedule_items
* assets (versions)
* overlay_profiles, overlay_bindings
* audit_log
* asrun_log

### 9.3. API (минимум)

* Assets: upload/list/get
* Channels: create/list/update
* Schedules: draft/publish/rollback
* Devices: enroll/assign/heartbeat
* Overlay: state update / stream subscribe
* Observability: health/status endpoints

---

## 10) Нефункциональные требования (SLO)

* API: P95 ≤ 300ms (внутреннее), P95 ≤ 800ms (публичное через интернет)
* SSE latency: P95 ≤ 2s от изменения данных до экрана (при нормальной сети)
* Контент: доставка выдерживает пиковое число экранов без падений (CDN)
* Масштаб: 100k устройств (архитектурно), 10k как ближайшая цель

---

## 11) План релизов (реально выполнимый)

### R0 — Pilot (4–6 недель)

* Каналы/расписание (простое)
* Ingest + базовая библиотека
* Device enroll + assignments + heartbeat
* Overlay SSE + 2–3 виджета
* Audit + basic as-run
* Минимальные алерты/дашборды

### R1 — Production hardening (6–10 недель)

* Квоты и биллинг-метрики (без оплаты, просто учёт)
* Улучшение fleet: remote commands, версии плеера, авто-обновления
* Улучшение overlay: state+patch, больше источников данных
* SSO/OIDC, расширенный RBAC

### R2 — Scale pack (после)

* Branch caching appliance / edge cache
* Offline режим (кэш плейлиста/контента)
* Enterprise policy, отчёты для комплаенса

---

## 12) Риски и решения

1. **Себестоимость трафика** → профили качества + лимиты + branch-cache roadmap.
2. **Разнообразие устройств** → жёстко выбираем “официальные” targets (например: Android box + Web kiosk; Tizen/webOS позже).
3. **Интеграции у клиентов разные** → коннекторы + “manual mode” для пилота.
4. **Операционная сложность** → read-only режим, audit, наблюдаемость, минимизация ручных процедур.
